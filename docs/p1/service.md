# P-1 · Documentation without folders: changes to the service (contract 1.3.0)

Date: 2026-10-26. Origin: the owner's decisions in `docs/jiku-web-backlog.md` (P-1) and the screen proposal
`_research/jiku-documentacion-propuesta-b/`. This document **prevails over `specification-v1.md`** where they
contradict each other, and it is the common reference for jiku-docs, jiku-go and the Jiku web.

## 1. Permissions: visibility instead of folders

The folder ACL no longer decides people's access. What decides is the caller's **class** and the document's
**visibility**.

| Visibility | `admin` | `user` | `external-user` | service (`internal-app`) |
| --- | --- | --- | --- | --- |
| `internal` (default) | reads and writes | reads and writes | never | everything |
| `public` | reads and writes | reads and writes | reads, if it is related to a project of their `project-permissions` | everything |
| `restricted` (new) | reads and writes | **never** | **never** | everything |

Rules:

- **What is invisible does not exist.** A `restricted` document does not exist for a `user` or an external user by **any path**: `documents.list`,
  `get`, `search` (and its snippets), `changes`, `versions.list`, `topics.list` (the counts do not count it), `attachments.*`,
  `shares.*`, `docs-notify`, `documents.suggest-relations`, the sync daemon's feed, and the counts of any
  response. It always responds `document_not_found` or omits it, just as today with what is not visible. Each path has its test.
- **Who changes the visibility:**
  - An internal person (`user` or `admin`) can set `internal` or `public`.
  - Only `admin` can set or remove `restricted`. A `user` who tries receives `permission_denied`.
  - Since the frontmatter is content, the rule is applied on every `new`, `update` and `restore`: a `user` cannot create a
    `restricted` document nor restore a version that would make it `restricted`.
- **Share links:**
  - Any internal person can create and revoke links of `internal` or `public` documents.
  - A `restricted` document does not accept links (`sharing_blocked`). Moving a document to `restricted` revokes its active
    links, just like deleting it.
- **Forcing the unlock:** `unlock` with `force` can be done by `admin`; it used to require `manage`.
- **Internal folders:** folders still exist, as the organisation of the files for the sync daemon, but they no
  longer define permissions for people.
  - `folders.*` and `folders.{id}.acl.replace` remain only for `admin` and services; for a `user` they respond
    `permission_denied`.
  - The ACL rules become **ineffective**: they are documented as deprecated in the contract, without deleting them from the database.
  - `externalBlocked` and `sharingBlocked` also become ineffective, replaced by the visibility.
- **Notifications:** `docs-notify` is computed with this model. A `restricted` document only notifies admins.

### Migration of existing data (without changing what each one sees today towards less safe)

When applying the migration:

1. Every document that today a person with the `user` role **cannot** read according to the current ACL becomes `restricted`. This
   includes `/imported/` and any folder without inheritance that has no rule for `user`.
2. Every `public` document in a folder with `externalBlocked` (effective, inherited) becomes `internal`, because today an
   external user does not see it.
3. The active links of the documents that become `restricted` are revoked (`revoke_reason = 'restricted'`).
4. The migration records each change in the document's history: a new service version with a message, because
   the visibility lives in the frontmatter.

## 2. Location generated by the server

- **Optional folder in `documents.new`.** If `folderId` is missing, the server generates the folder from the relations
  of the frontmatter, creating the missing folders:
  - with a project: `/clients/<client-slug>/<project-slug>/`; the client comes from the project according to core, or from the first of
    `jiku.clients`;
  - with a client and no project: `/clients/<client-slug>/general/`;
  - with neither client nor project: `/general/`.

  The slugs come from the names in core, in kebab-case without accents. With several projects the first one of the list is used.
- **Optional file name.** If `fileName` is missing, it is generated from the title in kebab-case `.md`, unique in the
  folder with a `-2`, `-3`, etc. suffix.
- **No automatic moves.** Changing relations later **does not move** the document: the location does not matter to
  people.
- **The UI never shows the path.** The `path` field stays in the responses for the CLI and sync.

## 3. Relations

- **New command `documents.{id}.relations.update`**, with `write` permission:
  - payload `{ baseVersion, add?: {clients, projects, requirements, tasks}, remove?: {...} }`;
  - it rewrites the `jiku:` block of the frontmatter without touching the rest of the content and creates a version (`kind = update`) with
    an automatic message (for example "Project assigned: EXO - Videoconferencia");
  - it validates the ids against core (`invalid_relation`) and responds `{ id, version, relations }`;
  - it is idempotent: if nothing changes, it responds `success` with the current version.

  It is what "Asignar proyecto" (assign project) uses. Adding a project also adds its client, if missing.
- **New query `documents.suggest-relations`**, with payload `{ id }` (requires `read`):
  - it returns up to 5 candidates `{ projectId, clientId, score, reason }`, taken from matches of names or aliases of
    core projects and clients in the title and in the content;
  - the title weighs more than the content;
  - it excludes the projects already related;
  - `reason` is a short text, for example "The title mentions “Videoconferencia”".

## 4. Lists and search

- **New filters** in `documents.list` and `documents.search`:
  - `hasProject`, `hasClient` and `hasTopic` (boolean). With `false` they implement "Sin proyecto" (no project), "Sin cliente" (no client) and
    "Sin tema" (no topic). "Sin proyecto" means no direct relation with a project, nor through a requirement nor through a task.
  - `visibility` accepts `restricted` (admin only; for the others it is `invalid_fields` or an empty list, and which one is documented).
- **Origin of the match by project.** With `filter.projectId`, each item carries `projectMatch`:
  - `direct`: the project is in `jiku.projects`;
  - `indirect`: the document arrives through a requirement or a task of the project.

  It is the basis of the "vinculado, sin proyecto propio" (related, without its own project) mark of the project card.
- **Author names.** `documents.list`, `get`, `search` and `versions.list` carry `createdByName` and `updatedByName`
  (and `authorName` in the versions).
  - The name is stored on write: `actor.name` (or `username`) when the api writes, the `name` from `users.list` when
    a person writes over the bus, and the service's name when a service writes.
  - If the api's `actor` carries neither `name` nor `username` (the web's token does not carry them, JIKU-WEB-5), the name is looked up
    in core's `users.list` before writing.
  - On read, a stored `null` name is filled in from core if it knows it, without writing it to the database. This way the
    documents written before the fix or while core was not responding show a name.
  - The name is not an access decision: if core does not respond it stays `null` and the operation goes on (there is no
    `upstream_unavailable`). In-memory cache: 10 min per name, 1 min for an id core does not know, 30 s without
    querying after a failure, 2 s of waiting at most.
  - A migration fills in the existing ones by querying core.
  - It is enough for "Editado por" (edited by) and for the lock: `lock.holderName`.
- **Clients and projects in the items.** Each item of `documents.list` and `search` includes `clients` and `projects` as
  lists of ids, to show "Cliente · Proyecto" (client · project). The names are resolved by the api with core.
- **Topics:** `topics.list` with `filter.prefix` already exists; it serves to suggest existing topics (free topics).

## 5. No changes

- History and compaction (`docs/history-compaction-v1.md`).
- Attachments (D-3).
- Events: new fields are added to `snapshot` (`visibility` already exists), without incompatible changes.
- Sync daemon: it mirrors according to `path`. With the new model, an internal person's files stop being read-only
  on disk, and `restricted` ones are synced only by admins.

## 6. Contracts and version

`jiku-docs-*.yaml` contracts to version **1.3.0**, with all of the above: visibility, new command and query, filters,
fields, ACL deprecations and errors. `meta.describe` reflects the new filters and fields. The v1
specification (sections 3, 4, 6, 7 and 11) and the CHANGELOG are updated.

## Implementation notes

Decisions taken while implementing (2026-10-26) in cases this document did not cover. Criterion: never expose a
`restricted` document; when in doubt, the most closed option.

**Permissions**

- **`admin` role:** it is `person-internal` with `admin` among its roles (`users.roles` over the bus, `actor.roles` with the api).
  A person with `external-user` and `admin` is still external (the most restrictive class wins, as in core).
- **Folders, queries:** `folders.list` and `folders.get` remain open to internal people, who see **all**
  folders (`effectivePermission`: `write` for `user`, `manage` for `admin` and services). A person's sync daemon
  needs them to know where it can create files. External users still do not see folders. Only the `folders.*`
  commands remain for `admin` and services. `include: [acl]` is only for `admin` and services.
- **Writing in folders:** an internal person writes documents in any folder (`documents.new` with `folderId`,
  `documents.{id}.move`). There is no longer a `permission_denied` by folder.
- **Links:** `shares.list` is visible to any internal person who reads the document; an external user receives `permission_denied`
  (they never manage links). `shares.{id}.revoke` can be done by any internal person who reads the document; on a link of
  a document they do not read it responds `share_not_found`. `shares.resolve` and `shares.attachment` respond `share_not_found`
  if the document is `restricted`, even if the link is still active (defence in depth: moving to `restricted` already revokes them).
- **`documents.new` with an existing `id`:** it only returns the document (idempotent retry) if whoever retries can
  read it; otherwise, `already_exists` without data.
- **`restricted` as a filter:** whoever does not read it receives an empty list (never `invalid_fields`).
- **Relations for external users:** in `clients` and `projects` of each item, and in `include: [relations]`, an external user receives
  only the projects of their `project-permissions` and no list of clients, requirements or tasks (they are internal ids,
  as in D-11). Before 1.3.0 `include: [relations]` returned everything to an external user.

**Generated location**

- A project without a client in core and without `jiku.clients` goes to `/clients/no-client/<project>/`.
- "The first one of the list" is the first one **as written** in the frontmatter (relations are stored
  sorted, but the service remembers the first of `jiku.projects` and of `jiku.clients`).
- A name that is not in core (catalogue cached 5 min) uses `project-<id>` or `client-<id>`; an empty slug, the same.
- The generated folders are created inheriting (as the service on behalf of whoever writes: `createdBy` is that person) and
  emit `folder.created`. Concurrent creations of the same folder are resolved by the unique index on paths.
- Without `fileName` and without a title (neither `title` nor `#`), the name is `document.md` (then `document-2.md`, …) and the title, `document`.
- The response of `documents.new` also carries `folderId` and `fileName`.

**`relations.update`**

- Payload `{ baseVersion, add?, remove?, sessionId? }`. **No `via`**: the origin comes from the caller's class (`human`
  for a person, `service` for a service). `sessionId` allows assigning while editing with one's own lock.
- Empty (or absent) `add` and `remove` are `invalid_fields`; an id in both as well. At most 100 ids per type.
- The client of an added project is added unless it is in `remove.clients`. Removing a project does not remove its
  client.
- The version is `kind: update` with an automatic `message` (therefore protected from the compaction): "Client assigned:
  Acmé S.A.; Project assigned: EXO - Videoconferencia". With an unknown name it uses `#<id>`.
- It rewrites only the lines of the `jiku:` block; comments inside that block are lost. A frontmatter written
  as a single map in flow style (`{title: x}`) is rewritten entirely.

**`suggest-relations`**

- Response `{ items: [{ projectId, clientId, score, reason }] }`, up to 5, `score` between 0 and 1 (2 decimals).
- **`projectId` is `null` in a client-only candidate** (never `0`): it appears when the text names a client
  and no project of that client matched. `clientId` is `null` if the project has no client.
- Terms of a project: the name, its parts separated by ` - `, `:`, `/`, `|`, and the code. Terms of
  fewer than 3 letters, numeric only or generic are ignored (`proyecto`, `general`, `interno`, `cliente`, `sistema`, `app`, `web`,
  `soporte`, `mantenimiento`, `desarrollo`; Spanish words, since project names are in Spanish: project, general, internal,
  client, system, app, web, support, maintenance, development). Title: 0.7; each mention in the content: 0.06 (up to 5); mention of the
  project's client: +0.1 in the title or +0.05 in the content. Whole-word matching, ignoring accents and
  case.
- It requires reading the document (deleted ones not included). An external user receives `permission_denied` (they would learn names of
  projects they do not see).

**Filters and names**

- `hasClient` looks only at `jiku.clients` (it does not infer the client from a project). `hasProject: true` is the exact
  complement of "Sin proyecto" (direct, through a requirement or through a task).
- `projectMatch` is added with `projectId` in the top-level filter or inside `or`.
- The items of `documents.search` also carry `createdBy`, `createdByName`, `updatedByName` and `visibility`.
- `document_locked` carries `holder`, `holderName`, `via` and `expiresAt` in `errorDetails`.
- A service's name is that of its row in core's `users`; the api's without an `actor`, `api`; that of jiku-docs
  itself, `jiku-docs`. Names are stored on write and are not updated if the person changes their name.
- `meta.describe` labels for `visibility`: Internal, Visible to the client, Restricted.

**Notifications**

- When a document becomes `restricted`, each `user` receives `access.changed` without detail; when it stops being `public`
  (to `internal` or `restricted`), the same for each external user with permission on any of the document's projects.
  Admins do not receive it (they keep reading it and receive the `document.updated`).

**Data migration**

- It runs in `serve`, after the SQL migrations and **before** registering the micro services: the service never
  serves with the new model on unmigrated data. If it fails, the process does not start.
- It is applied **only once** (`migration:p1-visibility` mark in `service_state`): a later change by an admin is not
  undone on restart. It is idempotent against an interruption: first it sets the `visibility` column and revokes the links of all
  the documents in one transaction and stores the plan; then it writes the versions one by one and skips those that already
  state the new visibility.
- "Can be read by a person with the `user` role" is evaluated with a principal that only has the `user` role: a rule for a
  specific `user-id` does not count, and that document becomes `restricted` (that person loses access; it is the safe side).
  A document in a deleted folder also becomes `restricted`. Deleted documents are migrated too.
- The migration's version is written by the jiku-docs service (`via: service`, protected), with `message`
  "P-1 migration: visibility restricted (…)" or "… internal (…)", and it updates the document's `updatedAt`/`updatedBy`. The
  `document.updated` carries `changes.visibility` from what the frontmatter said.
- It does not respect locks (it is a correction by the service); whoever held the lock receives `version_conflict` on the next save.
- A frontmatter that cannot be edited leaves the document with the column already changed (the safe option) and a warning in the log.
- Existing author names are filled in in the background from core's `users.list` (mark
  `migration:p1-names`), retrying every minute if core does not respond. An id core does not know stays with a `null` name.

**HedgeDoc importer**

- Unmapped notes (those in `/imported/`) are imported with `visibility: restricted`; those mapped to another folder,
  `internal`. The folder no longer decides anything.

**For the web and the api (pending)**

- Resolve with core the names of `clients` and `projects` of each item.
- "Editado por" and the lock: use `updatedByName` and `lock.holderName` (they can be `null` in old rows of ids core does not
  know).
- On `access.changed` there is no detail: reload the list.
- The visibility selector of the creation form: Internal (default) · Visible to the client · Restricted (the latter only for
  admin; the api can hide it from a `user`, the service responds `permission_denied` anyway).
